# ARTEX 블루팀 모드 사용 가이드

블루팀 모드는 보안 이벤트를 가져와 탐지 규칙으로 경보를 만들고, 케이스에 증거와 판단을 기록하는 방어 조사 공간입니다. 기존 침투 테스트 작업은 **레드팀 모드**에 그대로 남습니다. 두 모드는 로그인과 모델 설정을 공유하지만, 블루팀의 이벤트·규칙·경보·케이스는 레드팀의 공격 작업 그래프와 별도로 저장됩니다.

## 시작하기

1. 로그인한 뒤 왼쪽 위의 **Red / Blue** 전환기에서 **Blue**를 선택합니다. 선택은 브라우저에 저장되고, 블루팀 주소를 직접 열어도 해당 탐색 메뉴가 표시됩니다. 블루팀은 블루톤, 레드팀은 레드톤으로 자동 전환되며 라이트·다크 선택은 두 모드에서 유지됩니다.
2. **이벤트**에서 `.json`, `.jsonl`/`.ndjson`, `.csv` 파일을 업로드합니다. 화면에서 출처 이름을 지정할 수 있습니다.
3. **탐지 규칙**에서 이벤트 필드와 비교 방식을 정해 규칙을 만듭니다. 먼저 **시험**으로 기존 이벤트의 일치 결과를 확인한 다음 **실행**하여 과거 이벤트의 경보를 생성합니다. 이후 가져오는 이벤트에는 활성 규칙이 적용됩니다.
4. **경보**에서 상태와 심각도를 검토하고 케이스에 연결합니다. **케이스**에서는 사건 요약, 상태, 증거 타임라인과 관찰 내용을 관리합니다.
5. 필요한 경우 케이스의 **AI 분석**을 시작하고 결과를 검토합니다. 제안된 대응은 **대응 조치**에서 사람이 승인 또는 거절하고, 별도 절차에서 수행한 결과를 기록합니다.

대시보드는 케이스·이벤트·경보·규칙·승인 대기 조치의 집계를 보여줍니다. 케이스 상세 주소는 `/blue/cases/detail?id=<케이스 ID>`입니다.

## 이벤트 가져오기

파일 업로드는 한 요청에 최대 **8 MiB, 500건**을 받습니다. JSON 파일은 이벤트 객체 하나, 이벤트 배열 또는 `events` 배열을 담은 객체를, JSONL/NDJSON은 한 줄에 JSON 객체 하나를 사용합니다. CSV는 첫 줄을 열 이름으로 사용합니다. 파일의 각 이벤트에는 출처(또는 업로드 화면의 기본 출처), 발생 시각과 메시지가 필요합니다. 업로드한 원본 레코드는 `raw`에 보존되고, 시간·출처·이벤트 유형·심각도·자산·메시지는 검색 가능한 공통 필드로 정규화됩니다. 정규화 결과와 원본이 일치하는지 가져온 뒤 확인하세요.

인증된 클라이언트에서는 `POST /api/blue/events/import`에 JSON 요청을 보낼 수 있습니다. 기존 ARTEX 로그인에서 얻은 Bearer 토큰을 사용합니다.

```http
POST /api/blue/events/import
Authorization: Bearer <ARTEX access token>
Content-Type: application/json

{
  "events": [
    {
      "source": "lab-siem",
      "external_id": "evt-001",
      "event_type": "auth.failure",
      "severity": "medium",
      "asset": "lab-host",
      "message": "Failed sign-in",
      "occurred_at": "2026-10-21T00:00:00Z",
      "raw": {"user": "demo", "src_ip": "192.0.2.10"}
    }
  ]
}
```

같은 엔드포인트에 `multipart/form-data`의 `file`을 보내 파일로 가져올 수도 있습니다. 선택 필드 `format`은 `auto`, `json`, `jsonl`, `csv` 중 하나이고 `source`로 기본 출처를 지정할 수 있습니다. `source`와 `external_id`가 같은 이벤트를 다시 가져오면 중복 저장하지 않고 기존 이벤트를 반환할 수 있습니다. 한 요청의 실패는 그 묶음의 일부만 저장하지 않도록 처리됩니다. 응답의 `alerts_matched`는 기존 경보가 있는 일치 건도 포함한 규칙 일치 수이고, `alerts_created`는 새로 저장된 경보 수입니다. `detection_errors`와 `warnings`가 있으면 해당 규칙 평가 결과를 확인해야 합니다. 파일 업로드와 API 호출이 지원되는 수집 방식이며, 외부 SIEM 연결이나 상시 스트리밍 수집기는 포함되지 않습니다.

## 탐지 규칙과 경보

기본 규칙은 이벤트 필드 하나(`event_type`, `source`, `message`, `asset`, `severity`, `raw.user` 등)를 검사합니다. 화면에서는 `equals`, `contains`, `startswith`, `endswith`, `exists`, 숫자 비교(`gt`/`gte`/`lt`/`lte`)를 선택할 수 있습니다. 고급 JSON 정의는 여러 선택과 조건을 조합하는 **지원되는 Sigma 부분 문법**입니다. 정규식 비교(`re`)도 이 정의에서 지원합니다. 규칙 생성·수정 API에는 `sigma_yaml` 문자열을 보낼 수도 있으며, 서버가 지원 범위 안에서 JSON 정의로 변환해 저장합니다. 임의 코드나 Sigma 전체 문법을 실행하는 기능은 아닙니다. 지원되는 조건과 제한은 [탐지 규칙 형식](blue-team-detection-rules.md)에 정리되어 있습니다.

규칙의 **시험**(`POST /api/blue/rules/{id}/test`)은 저장된 이벤트의 일치 건수와 예시를 반환하며 경보를 만들지 않습니다. **실행**(`POST /api/blue/rules/{id}/run`)은 일치하는 과거 이벤트에 대해 규칙·이벤트 쌍으로 중복 제거된 경보를 저장합니다. 이후 새 이벤트를 가져오면 활성 규칙을 자동 평가합니다. 따라서 규칙을 새로 만든 직후에는 **실행**을 눌러 이미 저장된 이벤트도 검사하세요. 경보의 탐지 근거를 보존하기 위해 규칙 삭제 API는 제공하지 않으며, 사용을 중지할 때는 비활성화합니다. 규칙을 비활성화하거나 경보 상태를 바꿔도 네트워크 차단·격리 같은 외부 효과는 없습니다.

경보는 `new`, `investigating`, `confirmed`, `false_positive`, `dismissed` 상태로 분류할 수 있습니다. 경보를 케이스에 연결하면 사건 조사에서 해당 이벤트와 탐지 근거를 함께 볼 수 있습니다. 이벤트가 잘못된 케이스에 연결됐다면 API의 `POST /api/blue/events/{id}/move-case`에 `{"case_id": <새 케이스 ID>}`를 보내 해당 이벤트와 연결된 경보를 함께 이동할 수 있습니다. 이미 관찰 내용에서 그 이벤트나 경보를 증거로 인용했다면 이동을 거부합니다.

## 케이스, AI 분석, 대응 조치

케이스는 직접 만들거나 레드팀의 확인된 취약점에서 만들 수 있습니다. 상태는 `open` → `investigating` → `contained` → `resolved` → `closed` 등으로 기록합니다. 상태는 운영자가 실제 조사 진행에 맞춰 지정하는 값입니다. 케이스 상세 화면에서는 이벤트·경보·관찰 내용을 시간순으로 확인하고, 사실(`fact`), 가설(`hypothesis`), 미확인 사항(`unknown`), 권고(`recommendation`)를 구분해 메모를 남길 수 있습니다. 관찰 내용에는 관련 이벤트/경보 ID를 붙일 수 있습니다.

**AI 분석**은 해당 케이스에 연결된 이벤트나 경보가 있고 블루팀 분석 에이전트에 사용 가능한 모델이 설정되어 있을 때 시작할 수 있습니다. 저장된 증거를 바탕으로 비동기 실행되며 상태와 기록은 케이스에서 확인할 수 있습니다. 한 번의 분석에는 최근 이벤트 최대 40건과 경보 최대 40건을 전달하므로 사건의 모든 기록을 읽었다고 해석해서는 안 됩니다. 분석은 사실과 추정, 불확실성을 구분하고 이벤트/경보 ID를 근거로 제시하도록 설계되어 있습니다. 분석 결과의 **평가 심각도**는 모델이 증거를 보고 제시한 사건 영향이며 케이스·경보에 붙은 심각도와 별개입니다. 모델의 서술은 조사자를 대신하는 확정 판정이 아니므로 원본 이벤트와 근거 ID를 검증해야 합니다. 블루팀 분석에는 레드팀의 범용 셸·파일 수정·네트워크 공격 도구를 제공하지 않습니다.

AI의 대응 권고는 자동으로 조치 요청이 되지 않습니다. 조사자가 케이스 상세 화면에서 종류·대상·사유를 입력해 대응을 제안하면 `pending` 상태로 저장됩니다. **대응 조치** 화면에서 승인하면 `approved`, 거절하면 `rejected`가 됩니다. 승인된 조치에 대해 담당자가 별도 절차에서 실제로 수행한 결과와 티켓·로그·변경 기록 등의 근거를 입력하면 `completed` 또는 `failed`로 기록됩니다. **승인과 완료 기록 자체는 ARTEX가 외부 시스템에 조치를 실행했다는 뜻이 아닙니다.** 현재 화면은 방화벽 변경, 계정 차단, 호스트 격리 같은 외부 조치를 자동 실행하지 않습니다. 현행 인증은 단일 관리자 계정이므로 이 승인 기록은 독립 승인자에 의한 2인 결재나 실명 감사 기록을 대체하지 않습니다.

## 레드팀 결과 넘기기

레드팀의 **확인된 취약점** 상세 화면에서 **블루팀 케이스 만들기**를 선택하면 제목·심각도·요약을 가져온 케이스가 생성되고 원래 발견 항목과 연결됩니다. 블루팀 케이스에는 실제 탐지 이벤트와 조사 결과를 추가해 탐지 가능성과 대응 절차를 검증할 수 있습니다. 이 연결은 레드팀의 취약점 기록을 변경하거나 블루팀 경보를 자동으로 생성하지 않습니다.

## 주요 API

모든 `/api/blue/...` 경로는 기존 ARTEX 인증을 사용합니다. 자주 쓰는 경로는 다음과 같습니다.

| 작업 | 경로 |
| --- | --- |
| 집계 | `GET /api/blue/overview` |
| 케이스 조회·생성·수정 | `GET, POST /api/blue/cases`, `GET, PATCH /api/blue/cases/{id}` |
| 확인된 레드팀 발견 항목 연결 | `POST /api/blue/cases/from-finding` (`{"finding_id": <ID>}`) |
| 이벤트 조회·가져오기·케이스 수정 | `GET /api/blue/events`, `GET /api/blue/events/{id}`, `POST /api/blue/events/import`, `POST /api/blue/events/{id}/move-case` |
| 규칙 조회·수정·시험·실행 | `GET, POST /api/blue/rules`, `GET, PATCH /api/blue/rules/{id}`, `POST /api/blue/rules/{id}/test`, `POST /api/blue/rules/{id}/run` |
| 경보 조회·분류 | `GET /api/blue/alerts`, `GET, PATCH /api/blue/alerts/{id}` |
| 케이스 관찰 내용 | `GET, POST /api/blue/cases/{id}/observations` |
| AI 분석 시작·기록 | `POST /api/blue/cases/{id}/analyze`, `GET /api/blue/cases/{id}/analyses`, `GET /api/blue/analyses/{id}` |
| 대응 제안·결정·결과 기록 | `GET /api/blue/actions`, `GET, POST /api/blue/cases/{id}/actions`, `POST /api/blue/actions/{id}/decision`, `POST /api/blue/actions/{id}/complete` |

설계 배경과 데이터 경계는 [블루팀 아키텍처](blue-team-architecture.md)를 참고하세요.
