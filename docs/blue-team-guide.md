# ARTEX 블루팀 모드 사용 가이드

블루팀 모드는 보안 이벤트를 가져와 탐지 규칙으로 경보를 만들고, 사건에 증거와 판단을 기록하는 방어 조사 공간입니다. 기본 메뉴는 **대시보드·대화·작업·조사·LLM 기록·자산**이며, **조사**의 하위 메뉴는 **사건·이벤트·트래픽·탐지·대응 조치**입니다. 기존 침투 테스트 작업은 **레드팀 모드**에 그대로 남습니다. 두 모드는 로그인과 모델 설정을 공유하지만, 블루팀의 자산·이벤트·규칙·경보·사건은 레드팀의 공격 작업 그래프와 별도로 저장됩니다.

## 시작하기

1. 로그인한 뒤 왼쪽 위의 **Red / Blue** 전환기에서 **Blue**를 선택합니다. 선택은 브라우저에 저장되고, 블루팀 주소를 직접 열어도 해당 탐색 메뉴가 표시됩니다. 블루팀은 블루톤, 레드팀은 레드톤으로 자동 전환되며 라이트·다크 선택은 두 모드에서 유지됩니다.
2. **조사 → 이벤트**에서 `.json`, `.jsonl`/`.ndjson`, `.csv` 파일을 업로드하거나 HTTP JSONL **자동 수집 소스**를 등록합니다. 통신 기록이 들어오면 **조사 → 트래픽**에서 검색하고 원본 이벤트·연결된 사건으로 이동할 수 있습니다.
3. **조사 → 탐지 → 탐지 규칙** 탭에서 이벤트 필드와 비교 방식을 정해 규칙을 만듭니다. 먼저 **시험**으로 기존 이벤트의 일치 결과를 확인한 다음 **실행**하여 과거 이벤트의 경보를 생성합니다. 이후 가져오는 이벤트에는 활성 규칙이 적용됩니다.
4. **조사 → 탐지 → 경보** 탭에서 상태와 심각도를 검토하고 사건에 연결합니다. **조사 → 사건**에서는 사건 요약, 상태, 증거 타임라인과 관찰 내용을 관리합니다.
5. 사건에 연결된 증거를 AI로 검토하려면 사건의 **AI 분석**을 시작하거나 **작업**에서 조사할 질문을 제목·설명으로 적고 사건에 연결한 뒤 실행합니다. **대화**에서는 질문을 보낼 때 사건을 선택해 해당 사건의 제한된 증거를 함께 전달할 수 있습니다.
6. 사건·작업의 **보고서 다운로드**로 Markdown 결과물을 저장합니다. 제안된 대응은 **조사 → 대응 조치**에서 사람이 승인 또는 거절하고, 별도 절차에서 수행한 결과를 기록합니다.

대시보드는 케이스·이벤트·경보·규칙·승인 대기 조치의 집계를 보여줍니다. 케이스 상세 주소는 `/blue/cases/detail?id=<케이스 ID>`입니다.

사건·이벤트·경보·작업의 검색어는 서버에서 **전체 저장 기록에 적용한 뒤** 페이지를 나눕니다. 화면에 처음 표시된 50~100건만 검색하는 방식이 아닙니다. 일부 화면의 사건 선택 입력도 사건 ID로 검색할 수 있습니다.

## 블루팀 자산과 증거 연결

**자산**에서 조사 대상의 종류(`host`, `ip`, `domain`, `service`, `application`, `other`), 고유 식별자, 표시 이름과 메모를 등록합니다. 이 목록은 레드팀의 공격 대상 자산과 별개입니다. 자산을 더 이상 조사 대상으로 사용하지 않을 때는 삭제 대신 **보관** 상태로 바꿉니다. 기존 사건·이벤트·대응 기록의 연결은 보존되지만, 보관된 자산을 새 증거에 연결할 수는 없습니다.

**조사 → 사건**에서 자산을 직접 연결하거나 **조사 → 이벤트**에서 개별 이벤트의 자산을 지정할 수 있습니다. 사건의 자산 목록에는 직접 연결한 자산과 현재 그 사건에 속한 이벤트의 자산이 함께 나타납니다. 이벤트를 다른 사건으로 옮기면 이벤트를 통해 보이던 자산도 함께 이동합니다. 대응 조치의 자산 연결은 해당 자산의 활동 기록에 남으며 사건 자산 목록을 새로 구성하지 않습니다. 이벤트의 원래 `asset` 문자열과 대응 조치의 `target` 문자열은 수집·제안 당시의 기록으로 남고, `asset_id`는 조사자가 확인해 연결한 블루팀 자산 ID입니다. 기존 문자열을 추측해 자산 ID로 자동 변환하지 않습니다.

JSON 이벤트 가져오기에는 선택적으로 `asset_id`를 넣을 수 있습니다. 해당 ID는 활성 블루팀 자산이어야 하며, 중복 이벤트를 재수집해도 기존 이벤트의 자산 연결을 덮어쓰지 않습니다. HTTP JSONL 자동 수집에서는 피드가 보낸 `asset_id`를 신뢰해 자동 연결하지 않으므로, 가져온 이벤트를 확인한 뒤 필요하면 화면에서 연결하세요. 대응 조치를 제안할 때에도 사건의 자산 목록에 있는 활성 자산을 선택할 수 있습니다. 이 연결은 조사 기록이며 외부 시스템에 대한 조치 실행 권한을 부여하지 않습니다.

API에서는 `GET, POST /api/blue/assets`로 목록·등록, `GET, PATCH /api/blue/assets/{id}`로 조회·수정·보관, `GET /api/blue/assets/{id}/activity`로 관련 사건·이벤트·대응을 조회합니다. 사건의 자산은 `GET, POST /api/blue/cases/{id}/assets`와 `DELETE /api/blue/cases/{id}/assets/{assetID}`로 관리하고, 이벤트의 자산은 `PATCH /api/blue/events/{id}/asset`에 `{"asset_id": <ID>}` 또는 `{"asset_id": null}`을 보내 변경합니다. 직접 연결을 제거해도 그 사건의 이벤트에 같은 자산이 있으면 사건 자산 목록에 계속 나타납니다.

## 이벤트 가져오기

파일 업로드는 한 요청에 최대 **8 MiB, 500건**을 받습니다. JSON 파일은 이벤트 객체 하나, 이벤트 배열 또는 `events` 배열을 담은 객체를, JSONL/NDJSON은 한 줄에 JSON 객체 하나를 사용합니다. CSV는 첫 줄을 열 이름으로 사용합니다. 파일의 각 이벤트에는 출처(또는 업로드 화면의 기본 출처), 발생 시각과 메시지가 필요합니다. 업로드한 원본 레코드는 `raw`에 보존되고, 시간·출처·이벤트 유형·심각도·자산·메시지는 검색 가능한 공통 필드로 정규화됩니다. 정규화 결과와 원본이 일치하는지 가져온 뒤 확인하세요.

인증된 클라이언트에서는 `POST /api/blue/events/import`에 JSON 요청을 보낼 수 있습니다. 기존 ARTEX 로그인에서 얻은 Bearer 토큰을 사용합니다.

```http
POST /api/blue/events/import
Authorization: Bearer <ARTEX access token>
Content-Type: application/json

{
  "events": [
    {
      "source": "lab-siem",
      "external_id": "evt-001",
      "event_type": "auth.failure",
      "severity": "medium",
      "asset": "lab-host",
      "message": "Failed sign-in",
      "occurred_at": "2026-10-21T00:00:00Z",
      "raw": {"user": "demo", "src_ip": "192.0.2.10"}
    }
  ]
}
```

같은 엔드포인트에 `multipart/form-data`의 `file`을 보내 파일로 가져올 수도 있습니다. 선택 필드 `format`은 `auto`, `json`, `jsonl`, `csv` 중 하나이고 `source`로 기본 출처를 지정할 수 있습니다. `source`와 `external_id`가 같은 이벤트를 다시 가져오면 중복 저장하지 않고 기존 이벤트를 반환할 수 있습니다. 한 요청의 실패는 그 묶음의 일부만 저장하지 않도록 처리됩니다. 응답의 `alerts_matched`는 기존 경보가 있는 일치 건도 포함한 규칙 일치 수이고, `alerts_created`는 새로 저장된 경보 수입니다. `detection_errors`와 `warnings`가 있으면 해당 규칙 평가 결과를 확인해야 합니다.

## HTTP JSONL 자동 수집

**조사 → 이벤트 → 이벤트 자동 수집 소스**에 ARTEX 서버가 접근할 수 있는 HTTP(S) JSONL 피드의 이름과 URL을 등록합니다. 기본 수집 간격은 30초이며 10~3,600초로 조절할 수 있습니다. 등록 후 **지금 동기화**로 즉시 연결을 점검하거나 자동 수집을 끄고 다시 켤 수 있습니다. 오류와 마지막 성공 시각은 소스 목록에 표시됩니다. **커서 초기화**는 처음부터 다시 읽되 이미 저장된 이벤트를 지우지 않습니다. 소스를 삭제해도 가져온 이벤트·경보는 남습니다.

소스 서버는 `GET` 요청의 선택적 `cursor` 쿼리를 받아 그 위치 이후 기록을 JSONL로 응답하고, 다음 위치를 `X-ARTEX-Next-Cursor` 응답 헤더 하나에 담아야 합니다. 처음에는 `cursor`가 생략됩니다. 각 줄은 안정적인 `external_id`, 발생 시각, 메시지를 포함해야 합니다. `source`를 명시하면 그 라벨을 이벤트 출처로 유지하고, 생략하면 소스 이름과 무관한 `pull:<소스 ID>`를 사용합니다. ARTEX는 저장 성공 후에만 커서를 전진시키며, 같은 출처·외부 ID의 기록을 다시 받을 때는 중복을 막습니다. 명시한 출처 라벨을 바꾸면 같은 외부 ID도 별개 이벤트가 될 수 있으므로 라벨을 안정적으로 유지하세요. 동기화 응답의 `processed`는 중복 재처리를 포함한 처리 행 수이며 신규 이벤트 수가 아닙니다. 피드는 한 응답에 최대 8 MiB·500건이며 요청 제한 시간은 10초입니다. 리다이렉트는 따르지 않습니다.

등록 API는 `POST /api/blue/sources`이며 `{"name":"lab-http","url":"http://artex-lab-target:8080/logs/events"}`처럼 요청합니다. 목록은 `GET /api/blue/sources`, 수동 수집은 `POST /api/blue/sources/{id}/sync`, 설정·수집 중지·커서 초기화는 `PATCH /api/blue/sources/{id}` (`enabled`, `poll_interval_seconds`, `reset_cursor`)를 사용합니다. URL에는 사용자정보를 넣을 수 없고, 현재 소스별 인증 헤더 설정은 지원하지 않습니다. ARTEX가 내부 주소에도 접속하므로 관리자가 신뢰하는 피드만 등록하세요. 이 기능은 HTTP JSONL을 주기적으로 가져오는 방식이며 네트워크 패킷 센서나 모든 SIEM의 전용 커넥터를 대신하지 않습니다.

## 트래픽 조회

**조사 → 트래픽**은 가져온 블루팀 이벤트 중 통신 정보를 가진 기록을 서버에서 선별해 보여줍니다. 출처·프로토콜·검색어로 필터링하고 발생 시각 순으로 탐색할 수 있으며, 원본 JSON과 연결된 사건을 확인할 수 있습니다. 원본 이벤트의 사건 연결을 바꿀 때는 **조사 → 이벤트**로 이동합니다. 이 화면은 레드팀 에이전트의 프록시 기록과 별도이며, 네트워크 센서의 실시간 수집 기능은 포함하지 않습니다.

통신 기록을 가져올 때도 이벤트 가져오기의 필수 공통 필드인 `source`, `occurred_at` 또는 `timestamp`, `message`가 필요합니다. 파일 레코드의 최상위 필드 또는 API 요청의 `raw`에 출발지·목적지 주소, 포트, 프로토콜 또는 HTTP/DNS 정보를 남기면 트래픽 화면에서 세부 값을 볼 수 있습니다. 예를 들어 `src_ip`, `dest_ip`, `src_port`, `dest_port`, `proto`를 사용할 수 있습니다.

## Docker 테스트 자산으로 확인하기

[테스트 자산](../testdata/team-target/README.md)은 가짜 데이터만 담은 일회용 HTTP 서버입니다. `/debug/config`에는 의도적으로 노출한 더미 설정이 있으며, 요청마다 블루팀이 가져올 수 있는 JSONL 이벤트를 남깁니다. 저장소 루트에서 다음을 실행합니다. ARTEX의 Docker 네트워크 이름이 `artex-ko_default`가 아니면 링크된 안내에 따라 `ARTEX_DOCKER_NETWORK`를 설정하세요.

```powershell
New-Item -ItemType Directory -Force test-results/team-target | Out-Null
docker compose -f testdata/team-target/compose.yaml up --build -d
```

ARTEX 컨테이너에서 자산 주소는 `http://artex-lab-target:8080`입니다. 레드팀 대상에 이 주소를 사용하거나, 격리된 테스트 요청으로 `/`, `/api/items`, `/debug/config`, `/admin`을 호출합니다. 블루팀에서는 자동 수집 소스 URL로 `http://artex-lab-target:8080/logs/events`를 등록한 뒤 **지금 동기화**를 누릅니다. 이후 새 요청은 주기적 수집으로 들어오며 **조사 → 트래픽**에서 통신 필드를 확인할 수 있습니다. 생성된 `test-results/team-target/access.jsonl`을 **조사 → 이벤트**에서 직접 업로드하는 방식도 계속 지원합니다. 테스트 컨테이너만 종료하려면 `docker compose -f testdata/team-target/compose.yaml down`을 실행합니다.

## 탐지 규칙과 경보

기본 규칙은 이벤트 필드 하나(`event_type`, `source`, `message`, `asset`, `severity`, `raw.user` 등)를 검사합니다. 화면에서는 `equals`, `contains`, `startswith`, `endswith`, `exists`, 숫자 비교(`gt`/`gte`/`lt`/`lte`)를 선택할 수 있습니다. 고급 JSON 정의는 여러 선택과 조건을 조합하는 **지원되는 Sigma 부분 문법**입니다. 정규식 비교(`re`)도 이 정의에서 지원합니다. 규칙 생성·수정 API에는 `sigma_yaml` 문자열을 보낼 수도 있으며, 서버가 지원 범위 안에서 JSON 정의로 변환해 저장합니다. 임의 코드나 Sigma 전체 문법을 실행하는 기능은 아닙니다. 지원되는 조건과 제한은 [탐지 규칙 형식](blue-team-detection-rules.md)에 정리되어 있습니다.

규칙의 **시험**(`POST /api/blue/rules/{id}/test`)은 저장된 이벤트의 일치 건수와 예시를 반환하며 경보를 만들지 않습니다. **실행**(`POST /api/blue/rules/{id}/run`)은 일치하는 과거 이벤트에 대해 규칙·이벤트 쌍으로 중복 제거된 경보를 저장합니다. 검사는 최신 이벤트부터 시작하며, 한 묶음보다 오래된 기록이 있으면 화면에서 **이전 이벤트 이어서 검사**를 선택할 수 있습니다. API에서는 응답의 `has_more`와 `next_before_id`를 보고 다음 요청의 `before_id`로 이어서 검사합니다. 이후 새 이벤트를 가져오면 활성 규칙을 자동 평가합니다. 경보의 탐지 근거를 보존하기 위해 규칙 삭제 API는 제공하지 않으며, 사용을 중지할 때는 비활성화합니다. 규칙을 비활성화하거나 경보 상태를 바꿔도 네트워크 차단·격리 같은 외부 효과는 없습니다.

경보는 `new`, `investigating`, `confirmed`, `false_positive`, `dismissed` 상태로 분류할 수 있습니다. 경보를 케이스에 연결하면 사건 조사에서 해당 이벤트와 탐지 근거를 함께 볼 수 있습니다. 이벤트가 잘못된 케이스에 연결됐다면 API의 `POST /api/blue/events/{id}/move-case`에 `{"case_id": <새 케이스 ID>}`를 보내 해당 이벤트와 연결된 경보를 함께 이동할 수 있습니다. 이미 관찰 내용에서 그 이벤트나 경보를 증거로 인용했다면 이동을 거부합니다.

## 케이스, AI 분석, 대응 조치

케이스는 직접 만들거나 레드팀의 확인된 취약점에서 만들 수 있습니다. 상태는 `open` → `investigating` → `contained` → `resolved` → `closed` 등으로 기록합니다. 상태는 운영자가 실제 조사 진행에 맞춰 지정하는 값입니다. 케이스 상세 화면에서는 이벤트·경보·관찰 내용을 시간순으로 확인하고, 사실(`fact`), 가설(`hypothesis`), 미확인 사항(`unknown`), 권고(`recommendation`)를 구분해 메모를 남길 수 있습니다. 관찰 내용에는 관련 이벤트/경보 ID를 붙일 수 있습니다.

**AI 분석**은 해당 케이스에 연결된 이벤트나 경보가 있고 블루팀 분석 에이전트에 사용 가능한 모델이 설정되어 있을 때 시작할 수 있습니다. 저장된 증거를 바탕으로 비동기 실행되며 상태와 기록은 케이스에서 확인할 수 있습니다. 한 번의 분석에는 이벤트와 경보를 각각 최대 40건 전달합니다. 오래된 증거가 중요하면 해당 사건의 이벤트·경보 ID를 각각 최대 12개 지정할 수 있고, 선택 항목은 최근 기록보다 우선합니다. 다른 사건의 ID는 거부되며 선택 항목이 입력 크기 제한 때문에 빠질 상황에서도 실행을 거부합니다. 선택 ID는 분석 실행 기록에 남습니다. 그래도 사건의 모든 기록을 읽었다고 해석해서는 안 됩니다. 분석은 사실과 추정, 불확실성을 구분하고 이벤트/경보 ID를 근거로 제시하도록 설계되어 있습니다. 분석 결과의 **평가 심각도**는 모델이 증거를 보고 제시한 사건 영향이며 케이스·경보에 붙은 심각도와 별개입니다. 모델의 서술은 조사자를 대신하는 확정 판정이 아니므로 원본 이벤트와 근거 ID를 검증해야 합니다. 블루팀 분석에는 레드팀의 범용 셸·파일 수정·네트워크 공격 도구를 제공하지 않습니다.

**작업**은 사건에 연결한 뒤 실행합니다. 작업의 제목·설명은 일반 사건 분석과 별도의 조사 질문으로 모델에 전달되고, 우선순위는 업무 메타데이터로만 사용됩니다. 실행할 때 해당 사건의 오래된 이벤트·경보 ID를 각각 최대 12개 지정할 수 있습니다. 모델은 해당 작업에 대해 `answered`, `insufficient_evidence`, `out_of_scope` 중 하나로 답해야 합니다. 제공된 이벤트·경보 ID로 작업의 질문에 답할 수 있을 때만 완료되며, 증거가 부족하거나 읽기 전용 조사 범위를 벗어나면 차단 상태로 남습니다. 따라서 작업 결과를 확인할 때 질문에 맞는 답과 인용한 증거를 함께 검토하세요.

**대화**에서는 메시지를 보낼 때 사건을 선택하면 그 사건의 이벤트·경보를 제한된 크기의 스냅샷으로 첨부합니다. 필요하면 해당 사건의 오래된 이벤트·경보 ID를 각각 최대 12개 지정할 수 있으며, 선택 항목은 최근 기록보다 우선합니다. 모델은 첨부된 기록의 ID를 인용하고 누락되거나 잘린 증거를 표시하도록 지시받습니다. 한 번의 메시지에 이벤트와 경보 각각 최대 12건만 전달되며, 대화는 다른 사건이나 실시간 시스템을 직접 조회하지 않습니다. 사건에 근거한 최종 판단은 원본 기록과 사건의 AI 분석 결과에서 다시 확인하세요.

사건 상세와 작업 상세의 **보고서 다운로드**는 현재 저장된 사건·작업 정보와 관련 기록을 Markdown 파일로 내려받습니다. 사건 보고서에는 이벤트·경보·관찰·분석 실행·대응 기록이 포함되며, 각 항목은 최대 10,000건까지 수집하고 초과 시 잘림을 표시합니다. 보고서는 내려받은 시점의 스냅샷으로, 이후 기록 변경이 자동 반영되지는 않습니다.

**LLM 기록**은 기록 기능이 켜져 있을 때 저장된 블루팀 대화·사건 분석 요청과 응답만 표시합니다. 레드팀 기록은 이 목록과 상세에서 제외됩니다. 기록 설정은 레드팀과 공유하므로, 기록이 꺼져 있으면 이전에 저장된 항목 외에 새 호출이 나타나지 않습니다.

AI의 대응 권고는 자동으로 조치 요청이 되지 않습니다. 조사자가 케이스 상세 화면에서 종류·대상·사유를 입력해 대응을 제안하면 `pending` 상태로 저장됩니다. **대응 조치** 화면에서 승인하면 `approved`, 거절하면 `rejected`가 됩니다. 승인된 조치에 대해 담당자가 별도 절차에서 실제로 수행한 결과와 티켓·로그·변경 기록 등의 근거를 입력하면 `completed` 또는 `failed`로 기록됩니다. **승인과 완료 기록 자체는 ARTEX가 외부 시스템에 조치를 실행했다는 뜻이 아닙니다.** 현재 화면은 방화벽 변경, 계정 차단, 호스트 격리 같은 외부 조치를 자동 실행하지 않습니다. 현행 인증은 단일 관리자 계정이므로 이 승인 기록은 독립 승인자에 의한 2인 결재나 실명 감사 기록을 대체하지 않습니다.

## 레드팀 결과 넘기기

레드팀의 **확인된 취약점** 상세 화면에서 **블루팀 케이스 만들기**를 선택하면 제목·심각도·요약을 가져온 케이스가 생성되고 원래 발견 항목과 연결됩니다. 블루팀 케이스에는 실제 탐지 이벤트와 조사 결과를 추가해 탐지 가능성과 대응 절차를 검증할 수 있습니다. 이 연결은 레드팀의 취약점 기록을 변경하거나 블루팀 경보를 자동으로 생성하지 않습니다.

## 주요 API

모든 `/api/blue/...` 경로는 기존 ARTEX 인증을 사용합니다. 자주 쓰는 경로는 다음과 같습니다.

| 작업 | 경로 |
| --- | --- |
| 집계 | `GET /api/blue/overview` |
| 조사 작업 조회·생성·수정·실행 | `GET, POST /api/blue/tasks`, `GET, PATCH /api/blue/tasks/{id}`, `POST /api/blue/tasks/{id}/run` (선택적 `event_ids`, `alert_ids`) |
| 증거를 붙인 대화 | `POST /api/blue/conversations/{id}/messages` (`message`, 선택적 `case_id`, `event_ids`, `alert_ids`) |
| 케이스 조회·생성·수정 | `GET, POST /api/blue/cases`, `GET, PATCH /api/blue/cases/{id}` |
| 블루팀 자산 조회·등록·수정·관련 기록 | `GET, POST /api/blue/assets`, `GET, PATCH /api/blue/assets/{id}`, `GET /api/blue/assets/{id}/activity` |
| 케이스·이벤트 자산 연결 | `GET, POST /api/blue/cases/{id}/assets`, `DELETE /api/blue/cases/{id}/assets/{assetID}`, `PATCH /api/blue/events/{id}/asset` |
| 확인된 레드팀 발견 항목 연결 | `POST /api/blue/cases/from-finding` (`{"finding_id": <ID>}`) |
| 이벤트 조회·가져오기·케이스 수정 | `GET /api/blue/events`, `GET /api/blue/events/{id}`, `POST /api/blue/events/import`, `POST /api/blue/events/{id}/move-case` |
| HTTP JSONL 소스 등록·조회·수정·삭제·즉시 수집 | `GET, POST /api/blue/sources`, `PATCH, DELETE /api/blue/sources/{id}`, `POST /api/blue/sources/{id}/sync` |
| 가져온 네트워크 이벤트 조회 | `GET /api/blue/traffic` |
| 규칙 조회·수정·시험·실행 | `GET, POST /api/blue/rules`, `GET, PATCH /api/blue/rules/{id}`, `POST /api/blue/rules/{id}/test`, `POST /api/blue/rules/{id}/run` |
| 경보 조회·분류 | `GET /api/blue/alerts`, `GET, PATCH /api/blue/alerts/{id}` |
| 케이스 관찰 내용 | `GET, POST /api/blue/cases/{id}/observations` |
| AI 분석 시작·기록 | `POST /api/blue/cases/{id}/analyze` (선택적 `event_ids`, `alert_ids`), `GET /api/blue/cases/{id}/analyses`, `GET /api/blue/analyses/{id}` |
| 대응 제안·결정·결과 기록 | `GET /api/blue/actions`, `GET, POST /api/blue/cases/{id}/actions`, `POST /api/blue/actions/{id}/decision`, `POST /api/blue/actions/{id}/complete` |
| 블루팀 LLM 기록 | `GET /api/blue/llm/records`, `GET /api/blue/llm/records/{id}` |

사건·이벤트·경보·작업 목록은 `q` 검색어를 페이지 처리 전에 적용합니다. Markdown 보고서는 브라우저에서 관련 API를 조회해 만들며 별도의 보고서 생성 API는 없습니다. 설계 배경과 데이터 경계는 [블루팀 아키텍처](blue-team-architecture.md)를 참고하세요.

현재 블루팀은 파일·인증된 API 가져오기와 등록된 HTTP JSONL 피드의 주기적 수집을 지원합니다. 상시 패킷 센서나 외부 SIEM 전용 인증·프로토콜 커넥터는 없습니다. 승인된 대응 조치도 외부 시스템에서 실행하지 않고 사람이 수행한 결과를 기록합니다. 이 가이드의 AI 흐름은 코드와 모의 공급자 테스트를 기준으로 설명하며, 실제 구독 계정이나 API 모델을 연결한 실시간 실행은 검증하지 않았습니다.
